01 · Grunnmodellen

Hva er et operativsystem?

Kjerne

An operating system is software that manages a computer’s resources for its users and applications.

Et OS er laget som gjør begrenset og komplisert hardware brukbar for mange programmer og brukere. Applications kjører i et miljø operativsystemet tilbyr, mens operativsystemet formidler tilgangen til processors, memory, storage, network og andre I/O-devices.

User modeApplicationsApp + system libraries
Kontrollert kernel–user interface
Kernel modeOperating SystemFile system · virtual memory · networking · scheduling
Hardware Abstraction Layer
HardwarePhysical resourcesProcessors · memory · disk · graphics · network · I/O

Programmet ber om en tjeneste

En application skal normalt ikke måtte kjenne disk controlleren eller nettverkskortet. Den bruker et definert grensesnitt, og OS-et gjør det maskinvarespesifikke arbeidet.

Program→system call→OS service→hardware

M1-nivå: Forstå hvorfor grensesnittet finnes. Implementasjonen av system calls, interrupts og mode transfer kommer i senere moduler.

Kontrollspørsmål

Hvorfor er «OS-et er det grafiske skrivebordet» en for smal definisjon?

Vis forklaring

Et grafisk grensesnitt kan være en OS-tjeneste, men kjernen i definisjonen er forvaltning og abstraksjon av ressurser. Mange servere og embedded systems har et OS uten et vanlig desktop-grensesnitt.

02 · Mental modell

Referee, Illusionist og Glue

Quiz

De tre rollene er ikke tre separate deler av OS-et. De er tre måter å forstå hva en OS-funksjon bidrar med.

01

Referee

Fordeler delte ressurser, holder programmer adskilt og tillater kontrollert samarbeid.

Allocation
Hvem får CPU, memory, network bandwidth eller diskplass – og når?
Isolation
En feil eller et angrep i én application skal ikke spre seg til andre.
Communication
Grenser må kunne krysses på kontrollerte måter når programmer skal samarbeide.

02

Illusionist

Maskerer fysiske begrensninger og tilbyr enklere, mer fleksible virtuelle ressurser.

  • Hvert program kan oppleve en egen processor.
  • Begrenset RAM kan fremstå som et stort virtual memory.
  • Disk blocks kan fremstå som navngitte filer og mapper.

03

Glue

Tilbyr felles tjenester og standardiserte interfaces som gjør applications enklere å bygge og kombinere.

  • libraries og system services
  • file systems og networking
  • common UI services og datautveksling

Ett eksempel, alle tre roller

Forelesningen bruker file systems fordi samme funksjon viser hele modellen:

RefereePermissions begrenser hvem som kan lese og skrive en fil, også når lagringsplass gjenbrukes.
IllusionistEn navngitt fil kan vokse og fremstå som sammenhengende og varig, selv om lagringen består av fysiske blocks.
GlueDirectories og felles operasjoner lar forskjellige applications opprette, finne og dele data i samme format.
Husk: Referee fordeler og beskytter. Illusionist skjuler begrensninger. Glue tilbyr felles tjenester. En konkret OS-funksjon kan fylle flere roller samtidig.

03 · Problemet som må løses

Protection og untrusted applications

Kjerne

Et moderne system må kunne kjøre kode det ikke kan stole fullt på. Programmet kan være buggy, malicious eller compromised. Derfor kan det ikke få ubegrenset kontroll over maskinens ressurser.

Uten avgrensning kan et program
  • monopolisere CPU eller memory
  • lese eller overskrive andres data
  • korrumpere OS-et eller lagringen
  • forstyrre helt andre applications
→
Referee-rollen krever
  • resource allocation
  • fault isolation og protection
  • kontrollert communication
  • mulighet til å stoppe et program
Se M2 i moduloversikten →

Isolation betyr ikke at communication er unødvendig. Tvert imot må OS-et både etablere grenser og tilby trygge mekanismer for å krysse dem. Hvordan hardware og kernel håndhever dette kommer senere.

Eksempel fra forelesningen: Meltdown og Spectre viste at processor-optimaliseringer kunne åpne for datalekkasje på tvers av beskyttelsesgrenser. M1-poenget er at god isolation avhenger av både OS-design og hardware.
Eksamen · H2023 Hvorfor er application isolation viktig?

Oppgaven tester: om du skiller fault isolation fra CPU-deling og fra påstanden om at programmer aldri bør kommunisere.

Resonnement: En feil i én application skal være avgrenset slik at andre applications og OS-et kan fortsette. Communication kan fortsatt skje, men gjennom kontrollerte grensesnitt.

04 · OS challenges

Reliability, availability, security og privacy

Quiz

Disse ordene beskriver forskjellige kvaliteter. På quiz og eksamen må du kjenne igjen hvilket problem et scenario faktisk beskriver.

Reliability

Oppfører systemet seg korrekt?

Et reliable system gjør det det er designet for. En feil som sprer seg, corrupt data eller uventet OS-oppførsel er tegn på svak reliability.

Availability

Hvor mye av tiden virker systemet?

Availability forbedres når systemet feiler sjeldnere eller kommer raskere tilbake etter feil.

Systemet virkerMTTF ↑lengre tid før neste feil
→ feil →
Systemet repareresMTTR ↓kortere tid til gjenoppretting

Høyere MTTF eller lavere MTTR gir bedre availability.

Security

Kan systemet kompromitteres?

Handler om å motstå uautorisert kontroll eller misbruk av ressurser, blant annet gjennom protection, permissions og isolation.

Privacy

Hvem får tilgang til informasjon?

Data skal bare være tilgjengelig for autoriserte brukere. Et privacy-brudd kan skyldes angrep, bugs eller feilkonfigurasjon.

Eksamen · H2023 Hvordan kan availability forbedres?

Oppgaven tester: retningen på MTTF og MTTR.

Resonnement: Systemet bør holde seg oppe lenger mellom feil, altså høyere MTTF, og/eller bruke kortere tid på å komme tilbake, altså lavere MTTR.

Eksamen · H2024 Hvilket scenario viser svak OS reliability?

Scenario: En memory leak i ett program gjør at andre programmer slutter å svare.

Resonnement: Feilen er ikke lenger avgrenset til programmet som har buggen. OS-et har ikke opprettholdt den forventede fault isolation, og hele systemets korrekte oppførsel påvirkes.

05 · Abstraction mellom lag

Portability

Quiz

Portability handler om å begrense hvor mye kode som må kjenne én bestemt maskin. Forelesningen skiller mellom portability for applications og for selve OS-et.

Applications

API og abstract virtual machine

Et Application Programming Interface gir programmet stabile operasjoner. Miljøet OS-et presenterer kan forstås som en abstract virtual machine: en mer nyttig og kontrollert plattform enn raw hardware.

06 · Mål og avveininger

Performance og trade-offs

Kjerne

«Rask» er for upresist. Et OS vurderes gjennom flere metrics som kan peke i forskjellige retninger.

Latency / response time
Hvor lang tid én operasjon bruker. Eksempel: tiden fra et klikk til svaret vises.
Throughput
Hvor mange operasjoner systemet fullfører per tidsenhet. Eksempel: requests per second.
Overhead
Ekstra arbeid OS-et gjør for å levere tjenesten, som scheduling og context switching.
Fairness
Hvor jevnt brukere eller programmer får service og ressurser.
Predictability
Hvor stabil performance er over tid; liten variasjon kan være viktigere enn et raskt enkelttilfelle.

Time quantum: responsiveness mot overhead

Kort time quantum

  1. hyppigere scheduling
  2. flere context switches
  3. høyere overhead
  4. potensielt bedre responsiveness

Langt time quantum

  1. sjeldnere scheduling
  2. færre context switches
  3. lavere overhead
  4. potensielt svakere responsiveness

Det riktige valget avhenger av workload og mål. Et interactive desktop-system prioriterer gjerne respons, et batch system samlet arbeid, mens en server ofte må balansere throughput, response time, fairness og resource utilization.

Eksamen · H2024 Drøft kort mot langt time quantum i Round Robin

Oppgaven tester: en årsakskjede, ikke bare definisjonene.

Modellsvar: Et kort quantum kan gi raskere respons fordi flere jobs får CPU oftere, men hyppige context switches øker overhead og kan redusere tiden til nyttig arbeid. Et langt quantum reduserer denne overheaden og lar hver process gjøre mer per tur, men andre jobs kan vente lenger.

Eksamen · H2025 Hva skjer med overhead når time quantum økes?

Resonnement: Lengre quantum gir vanligvis færre context switches for samme arbeidsmengde. Dermed går mindre tid til schedulerens byttearbeid, og overhead synker.

07 · Hvorfor systemene utviklet seg

Historie og virtualization

Quiz

Historien er nyttig når den forklarer prioriteringene: først var computer time dyrt, senere ble interactive user time viktig, og dagens systemer må støtte mange maskintyper, users og workloads.

  1. 01

    Direct hardware use

    Én application om gangen hadde stor kontroll over hardware. OS-et lignet mer på et runtime library, og protection var begrenset.

  2. 02

    Batch systems

    Jobs ble lagt i kø slik at neste jobb kunne lastes automatisk og CPU-en holdes opptatt. Resource utilization økte, men brukeren ventet uten interaktivitet.

  3. 03

    Time-sharing og multiprogramming

    Flere users og programmer var aktive samtidig. CPU-tid ble delt, og rask menneskelig respons ble viktigere.

  4. 04

    Modern systems

    Smartphones, laptops, servers, embedded devices, virtual machines og data centers bruker fortsatt de samme grunnideene: sharing, protection, abstraction og common services.

  5. 05

    Videre utvikling

    Flere processors per maskin, flere maskiner per bruker og svært stor lagring gjør koordinering og systemdesign stadig viktigere.

Bare metal eller OS?

Bare metal

Én avgrenset oppgave

Et lite embedded system med én bestemt funksjon og få ressurser kan kjøre programmet direkte på hardware og unngå unødvendig kompleksitet.

Operating System

Mange ting må koordineres

Når systemet trenger flere applications, devices, users, networking, files og beskyttelse, gir OS-abstraksjonene stor verdi.

Virtualization er en Illusionist-mekanisme

Virtualization gir en application eller et guest OS en illusjon av ressurser som ikke nødvendigvis finnes i den formen fysisk. En guest kan oppleve egen CPU, memory, storage og network selv om disse deles.

VM 1VM 2VM 3
↓
Virtualization layer / hostfordeler og presenterer virtuelle ressurser
↓
Physical hardwareCPU · memory · storage · network
Eksamen · H2024 Hva betyr virtualization i OS-kontekst?

Oppgaven tester: om du kjenner Illusionist-rollen og ikke blander virtualization med protection eller common services.

Resonnement: Virtualization presenterer en illusjon av ressurser som kan være annerledes, større eller ikke fysisk til stede i samme form.

08 · Skill begrepene

Typiske misforståelser

  • Et OS er ikke bare et GUI.Det avgjørende er ressursforvaltning, abstraction, protection og tjenester.
  • Isolation betyr ikke «ingen communication».OS-et må både beskytte grenser og tilby kontrollert samarbeid.
  • Reliability og availability er ikke synonymer.Det første handler om korrekt oppførsel; det andre om hvor mye av tiden tjenesten virker.
  • Lav latency betyr ikke automatisk høy throughput.Én request kan være rask selv om systemet håndterer få requests totalt – og omvendt.
  • Virtualization er mer enn å starte VirtualBox.Kjerneideen er illusjonen av ressurser som ikke finnes fysisk i samme form.
  • Mer frequent scheduling er ikke gratis.Bedre responsiveness kan koste mer context-switch overhead.

10 · Hent frem uten notater

Active recall

Prøv å svare muntlig eller skriftlig før du åpner modellsvaret. Forklar sammenhengen – ikke bare enkeltordet.

1. Definer et operating system og tegn de tre hovedlagene.

Et OS er software som forvalter en datamaskins ressurser for users og applications. Modellen er Users/Applications → Operating System → Hardware.

2. Hvorfor er OS-et både et grensesnitt og en ressursforvalter?

Det tilbyr enklere, standardiserte operasjoner mot hardware samtidig som det avgjør hvem som får bruke begrensede ressurser, når og under hvilke rettigheter.

3. Forklar Referee, Illusionist og Glue med én setning hver.

Referee fordeler og beskytter delte ressurser. Illusionist maskerer hardware-begrensninger gjennom virtuelle abstractions. Glue tilbyr common services og interfaces som applications kan bygge på.

4. Hvordan kan et file system fylle alle tre OS-rollene?

Det håndhever permissions (Referee), skjuler disk blocks bak navngitte filer (Illusionist) og tilbyr felles fil- og directory-operasjoner (Glue).

5. Hvorfor må isolation og communication eksistere samtidig?

Isolation hindrer feil og angrep i å spre seg. Applications må likevel kunne samarbeide og dele data, så OS-et tilbyr kontrollerte mekanismer som krysser grensene.

6. Sammenlign reliability og availability.

Reliability spør om systemet oppfører seg korrekt. Availability spør hvor stor del av tiden systemet er fungerende og tilgjengelig.

7. Hvordan påvirker MTTF og MTTR availability?

Høyere Mean Time To Failure betyr sjeldnere feil. Lavere Mean Time To Repair betyr raskere gjenoppretting. Begge forbedrer availability.

8. Skillet mellom security og privacy – hva er det?

Security handler om å motstå kompromittering og uautorisert kontroll. Privacy handler om at informasjon bare er tilgjengelig for autoriserte parter.

9. Hvilke lag bidrar til portability for application og OS?

Application-kode bruker API-et og den abstract virtual machine OS-et presenterer. OS-et bruker en Hardware Abstraction Layer for å isolere maskinvarespesifikk kode.

10. En tjeneste svarer på 90 ms og håndterer 12 000 requests/s. Hvilke metrics er oppgitt?

90 ms beskriver latency/response time for én operasjon. 12 000 requests per sekund beskriver throughput.

11. Hvorfor kan et system være raskt, men lite predictable?

Et lavt gjennomsnitt kan skjule stor variasjon. Hvis noen requests er svært raske og andre svært trege, er performance lite konsistent selv om enkelte svar er raske.

12. Forklar trade-offen mellom kort og langt time quantum.

Kort quantum gir hyppigere CPU-tilgang og kan bedre responsiveness, men flere context switches gir mer overhead. Langt quantum gjør motsatt.

13. Hvorfor oppstod batch systems og senere time-sharing?

Batch systems holdt dyre datamaskiner i arbeid ved å køe jobs. Da interaktiv bruk og user time ble viktigere, lot time-sharing flere users/programmer dele CPU-en med raskere respons.

14. Når kan bare metal være rimelig, og hva er virtualization på M1-nivå?

Bare metal kan passe en enkel embedded enhet med én oppgave og lite behov for koordinering. Virtualization er å presentere en illusjon av ressurser som ikke nødvendigvis finnes fysisk i samme form.
