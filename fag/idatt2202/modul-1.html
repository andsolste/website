Grunnmodellen

Hva er et operativsystem?

An operating system is software that manages a computer's resources for its users and applications.

Operativsystemet ligger mellom programmene og den fysiske maskinvaren. Hardware-laget omfatter blant annet CPU/processors, memory, disks/storage, network interfaces, graphics processors og andre I/O-devices som tastatur og mus.

Users / Applications Applications og system libraries · user mode
↓
Operating System OS services · kernel mode
↓
Hardware CPU · memory · storage · network · I/O

Applikasjoner skal normalt ikke kontrollere hardware direkte. OS-et tilbyr abstraksjoner og grensesnitt som gjør maskinvaren enklere og tryggere å bruke. Programmet trenger derfor ikke vite hvordan en disk, et nettverkskort eller en annen device fungerer fysisk.

System calls: kontrollert tilgang til OS-tjenester

Et program ber operativsystemet utføre operasjoner gjennom system calls. I denne modulen er hovedpoenget selve grensesnittet; detaljene kommer senere.

Program→system call→OS service→hardware

Eksempler: open(), read(), write(), create process og allocate memory.

Ett OS · tre roller

Referee, Illusionist og Glue

De tre rollene forklarer hvorfor operativsystemet både må fordele, skjule og binde sammen ressurser.

01

Referee

Fordeler ressurser og beskytter programmer og brukere mot hverandre.

Resource allocation
Hvem får CPU, memory, disk eller network interface – og hvor lenge?
Isolation
Et program skal ikke lese eller overskrive et annet programs minne uten tillatelse. Et untrusted game skal for eksempel ikke kunne hente data fra en banking application.
Controlled communication
Programmer isoleres når de skal være separate, men får kontrollerte mekanismer for samarbeid.

02

Illusionist

Skjuler den fysiske virkeligheten og presenterer enklere eller større virtuelle ressurser.

  • Raske bytter A → B → C kan få hvert program til å oppleve at det har CPU-en.
  • Prosesser kan oppleve at de har hvert sitt memory address space, selv om fysisk RAM deles.
  • En virtual machine kan oppleve egen CPU, RAM, disk og network card.

03

Glue

Binder applications og hardware sammen gjennom standardiserte tjenester og abstraksjoner.

En webserver kan motta en HTTP request, finne data og sende et svar uten selv å implementere Ethernet-driver, TCP, disk controller, hardware interrupts eller low-level memory management.

System libraries · system calls · file systems · networking · user-interface services

Husk: Referee fordeler og beskytter. Illusionist skjuler og virtualiserer. Glue tilbyr felles tjenester og grensesnitt.

File systems viser alle tre rollene

RefereeOS-et kontrollerer hvem som kan lese og skrive filer.

Glueopen, read, write og close gir et praktisk felles grensesnitt.

Kontroll og mål

Protection og resource allocation

Hvordan kjører vi en untrustworthy application trygt?

Et program kan være buggy, malicious, compromised eller bare dårlig programmert. Det må likevel kunne kjøre uten å kompromittere hele maskinen.

Programmet må ikke kunne
  • lese vilkårlig memory eller endre kernel memory
  • kontrollere hardware fritt
  • ta all CPU-tid eller bruke all memory
  • ødelegge andre prosesser

Viktig prinsipp: OS security depends on both software and hardware. Meltdown og Spectre brukes her som påminnelse om at svikt i hardware-mekanismene kan bryte antakelsene OS-et bruker for process isolation.

Riktig ressursfordeling avhenger av systemets mål

Det finnes ikke nødvendigvis én riktig scheduling policy. Workload og mål avgjør hva som bør prioriteres.

Desktop

Brukeren forventer rask respons. Low response time står sentralt.

Batch system

Store jobs kjører med lite interaksjon. Job completion og samlet effektivitet/resource utilization kan veie tyngst.

Server

Mange requests gjør throughput, fairness, response time og resource utilization relevante samtidig.

Scheduling policy depends on workload and goals.

Kvalitetsmål

Operating System Challenges

Et OS skal ikke bare fungere. Det skal fungere korrekt, være tilgjengelig, beskytte data og kunne brukes på ulike systemer.

Reliability

Gjør systemet det det er designet for?

Crashes, corrupt data, feil scheduling, feil resultater eller at et program påvirker feil process er reliability-problemer.

Availability

Hvor mye av tiden virker systemet?

MTTF er gjennomsnittlig tid før feil – høy er bra. MTTR er gjennomsnittlig tid til gjenoppretting – lav er bra.

Availability forbedres ved å feile sjeldnere eller recover faster.

Security

Kan systemet kompromitteres?

OS-et må kontrollere access to resources, process isolation, permissions og authentication/authorization-relaterte mekanismer.

Privacy

Hvem kan se informasjonen?

Data skal bare være tilgjengelig for dem som har lov. Bugs og feilkonfigurasjon kan lekke privat informasjon selv uten et aktivt angrep.

Mål og avveininger

Performance og trade-offs

Performance er mer enn hvor «rask» maskinen er. Fem metrics beskriver ulike sider ved systemet.

Latency / response time
Tiden én operasjon bruker. Lav latency er særlig viktig i interactive systems.
Throughput
Antall operasjoner per tidsenhet, for eksempel requests per second.
Overhead
OS-arbeid som ikke direkte utfører brukeroppgaven, som et context switch.
Fairness
Hvor likt service eller performance fordeles mellom brukere og programmer.
Predictability
Hvor konsistent systemets performance er fra operasjon til operasjon.
Latency er ikke throughput: Et system kan ha god latency, men lav throughput – eller høy throughput, men dårlig latency.

Time slice: responsiveness mot overhead

Short time slice

  1. Flere context switches
  2. Mer overhead
  3. Potensielt bedre responsiveness

Long time slice

  1. Færre context switches
  2. Mindre overhead
  3. Potensielt dårligere responsiveness

OS-design er balansering

Performance, security, reliability, fairness, resource utilization, responsiveness og portability kan trekke i ulike retninger. Det finnes sjelden én universelt beste løsning.

  • Mer isolationkan gi mer overhead
  • Hyppigere schedulingkan gi bedre responsiveness, men mer overhead
  • Aggressiv resource utilizationkan gi bedre throughput, men dårligere latency
  • Mer fairnessmå ofte veies mot throughput eller latency

Fra maskintid til brukertid

Utvikling og moderne systemer

Historien forklarer hvorfor OS-prioriteringene har flyttet seg, selv om de grunnleggende problemene fortsatt er de samme.

  1. 01

    Early systems

    Datamaskiner var dyre. Én application kjørte om gangen, hadde stor kontroll over hardware og møtte lite protection. Brukere ventet på tilgang.

  2. 02

    Batch systems

    Jobs ble lagt i kø, og systemet startet automatisk neste jobb. Resource utilization ble bedre, men brukeren hadde lite eller ingen interaktiv kontakt.

  3. 03

    Time-sharing og multiprogramming

    Flere brukere og programmer kunne være aktive samtidig. CPU-en ble delt, og fokuset flyttet seg fra bare computer time mot human/user time.

  4. 04

    Modern systems

    Smartphones, laptops, tablets, servers, virtual machines, data centers og embedded systems bruker fortsatt allocation, protection, concurrency, virtualization, storage og communication.

Bare metal eller et fullverdig OS?

Bare metal

Én bestemt oppgave

Et enkelt microcontroller-/coffee-roaster-system med begrenset hardware og uten behov for flere applications kan kjøre direkte på hardware. Et OS kan da gi unødvendig kompleksitet og overhead.

Operating system

Mange ressurser må koordineres

Et Raspberry Pi-/RetroPie-system med input, display, sound, file system, networking og flere services har stor nytte av OS-abstraksjoner og resource management.

Jo flere programmer, devices, users og resources som skal koordineres, desto større verdi gir operativsystemet.
