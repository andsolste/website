Beskriv UI fra data

React og components

React er et JavaScript library for å bygge user interfaces av gjenbrukbare components.

React er komponentbasert og deklarativt. Utvikleren beskriver hvordan grensesnittet skal se ut for en gitt state, og React sørger for å oppdatere relevant UI når state endres.

Imperativ tankegang

Utfør DOM-steg

Finn elementet → endre tekst → skjul noe → vis noe → endre class.

Deklarativ React

Beskriv resultatet

state = loggedIn → render UI-et som passer denne tilstanden.

React spør først: «Hvordan skal UI se ut gitt disse dataene?»

Fra UI til component hierarchy

En component er en gjenbrukbar del av grensesnittet med et tydelig ansvar. Målet er ikke flest mulig components, men grenser som gjør løsningen forståelig og vedlikeholdbar.

  • App
    • Header

  • Components deler opp ansvar.
  • Samme struktur kan gjenbrukes med forskjellige data.
  • Hierarkiet gjør det lettere å se hvor data bør eies og sendes.

React bruker en Virtual DOM som del av arbeidet med å finne nødvendige UI-oppdateringer. Her er det nok å vite at React evaluerer UI-et igjen og oppdaterer det som må endres; interne detaljer kommer ikke først.

UI i JavaScript og TypeScript

JSX og functional components

JSX er en syntax extension som lar oss beskrive React-elementer med HTML-lignende syntaks inne i JavaScript eller TypeScript. JavaScript expressions settes inn med krøllparenteser.

const title = "Webutvikling";

function Greeting() {
    return (
        <section className="card">
            <h1>{title}</h1>
        </section>
    );
}
Lowercase
Native HTML-elementer skrives som section, h1 og button.
Stor bokstav
Egne React components skrives som UserCard og brukes som <UserCard />.
className
JSX bruker className i stedet for HTML-attributtet class.
{ }
Krøllparenteser lar JSX bruke JavaScript expressions.

Moderne React bruker hovedsakelig functional components og hooks. Class components finnes historisk, men er ikke hovedmodellen i dette emnet.

Input og endring

Props, state og rendering

Props flytter data nedover

interface UserCardProps {
    name: string;
}

function UserCard({ name }: UserCardProps) {
    return <p>{name}</p>;
}

<UserCard name="Andreas" />
<UserCard name="Ola" />
<UserCard name="Kari" />

Component-strukturen er den samme, mens data varierer gjennom props. Fra child-perspektivet behandles props som read-only.

Component + props → UI

State driver det som kan endres

State er data som kan endres mens applikasjonen kjører og som påvirker UI, for eksempel et søk, valgt element, aktiv fane eller om en dialog er åpen.

const [count, setCount] = useState(0);

<button onClick={() => setCount(count + 1)}>
    Count: {count}
</button>
PropsState
Kommer fra parentEies av en component
Read-only for childKan oppdateres med Reacts mekanismer
Input og configurationPåvirker rendering når verdien endres
De henger sammen: State hos en parent kan sendes videre som props til en child.

Rendering er ikke full DOM-utskifting

Når relevante data endres, kjøres component-logikken igjen for å beskrive ønsket UI. Det betyr ikke at hele DOM-en nødvendigvis skrives på nytt; React oppdaterer det som må endres.

En vanlig lokal variabel er ikke state. Hvis en verdi skal endre hva React viser, må React normalt kjenne til endringen gjennom state eller annen React-dataflyt.

Handlinger tilbake opp

Events og callbacks

Brukerhandlinger utløser funksjoner. Funksjonene kan oppdatere state direkte eller kalle en callback som en parent har sendt ned som prop.

<button onClick={handleClick}>
    Save
</button>

<button onClick={() => setOpen(true)}>
    Open
</button>

Data ned

Parent → props → child

Parent sender verdier og funksjoner til child.

Handlinger opp

Child → callback → parent

Child kaller funksjonen slik at eieren kan oppdatere state.

interface ChildProps {
    onSelect: (id: string) => void;
}

function Parent() {
    const [selected, setSelected] = useState("");

    return <Child onSelect={setSelected} />;
}

function Child({ onSelect }: ChildProps) {
    return (
        <button onClick={() => onSelect("item-1")}>
            Select
        </button>
    );
}

Én tydelig eier

Hvor skal state ligge?

State bør ligge hos den nærmeste felles componenten som trenger å eie dataene. Når flere sibling-components trenger samme verdi, flyttes state ofte opp til deres nærmeste felles parent. Dette kalles lifting state up.

  • App · query state
    • SearchInput · får setter/callback
    • ResultList · får query som prop
Single source of truth: Unngå unødvendige kopier av samme state flere steder. Én eier gjør det mindre sannsynlig at verdiene kommer ut av sync.
Liten component
Local state er ofte nok.
Noen components
Lift state og bruk props og callbacks.
Mange components i et subtree
Context kan bli relevant.
Større kompleksitet
Egnet global state management kan bli aktuelt, men ikke før problemet krever det.

Props og local state er standardvalget når dataflyten er enkel.

React-funksjonalitet i components

Hooks og useEffect

Hooks lar functional components bruke React-funksjonalitet som state, effects og Context. I denne modulen er useState, useEffect og useContext de viktigste.

useEffect brukes til side effects som følger av rendering eller endringer i data.

useEffect(() => {
    document.title = "Count: " + count;
}, [count]);

Første argument er effect-funksjonen. Dependency arrayen [count] sier at effekten skal kjøres når count endres.

  • synkronisering med systemer utenfor React
  • datahenting på overordnet nivå
  • subscriptions og event listeners
  • browser APIs
Ikke bruk useEffect automatisk: Hvis en verdi kan beregnes direkte fra props eller state under rendering, trenger den ofte ikke en effect.

Noen effects trenger cleanup, men avansert lifecycle- og cleanup-logikk er ikke målet her. API- og datahenting behandles videre i Modul 3.

Delt data i et subtree

Context

Når mellomliggende components bare videresender samme prop gjennom mange nivåer, får vi prop drilling. Context kan gjøre delt data tilgjengelig i et subtree uten at hvert nivå må sende prop-en videre.

  • App / Provider
    • Layout
      • Page
        • Toolbar
          • Button · useContext
const ThemeContext = createContext("light");

function App() {
    return (
        <ThemeContext.Provider value="dark">
            <Page />
        </ThemeContext.Provider>
    );
}

function Page() {
    const theme = useContext(ThemeContext);
    return <p>{theme}</p>;
}

Bruk props

Enkel parent → child-flyt

Data skal bare ett eller få nivåer ned, og eierskapet er tydelig.

Vurder Context

Delt data i et subtree

Flere components trenger samme data, eller prop drilling gjennom mange nivåer blir upraktisk.

Context er ikke automatisk bedre enn props. Unngå over-engineering.

Persistence i browseren

Web Storage

React state og persistent lagring løser forskjellige problemer. State driver den kjørende UI-tilstanden, mens Web Storage kan bevare data i browseren.

React state

Tilstand i applikasjonen

Eksisterer i den kjørende React-applikasjonen og påvirker rendering.

Web Storage

Data i browseren

localStorage beholdes mellom besøk. sessionStorage varer for tabben eller sessionen.

localStorage.setItem("theme", "dark");

const theme = localStorage.getItem("theme");

For større og mer strukturerte lokale datasett finnes IndexedDB. Det er nok å kjenne til dette alternativet nå.

Samlemodellen

Hele dataflyten

React blir lettere å lese når du følger hvem som eier data, hvordan data går ned, og hvordan handlinger kommer tilbake til eieren.

Ett sammenhengende eksempel

interface SearchProps {
    query: string;
    onQueryChange: (query: string) => void;
}

function App() {
    const [query, setQuery] = useState("");

    return (
        <>
            <Search
                query={query}
                onQueryChange={setQuery}
            />
            <p>Du søker etter: {query}</p>
        </>
    );
}

function Search({ query, onQueryChange }: SearchProps) {
    return (
        <input
            value={query}
            onChange={(event) =>
                onQueryChange(event.target.value)
            }
        />
    );
}
  1. App eier state.query og setQuery opprettes med useState.
  2. Data går ned.query sendes til Search som prop.
  3. En callback går ned.onQueryChange peker til state-oppdateringen hos App.
  4. En handling skjer i child.Input-eventet oppstår i Search.
  5. Handlingen går opp.Callbacken oppdaterer state hos App.
  6. UI rendres med nye data.React viser den oppdaterte query-verdien.

Fallgruver og kodelesing

  1. Vanlig variabel som stateForventer at UI oppdateres uten Reacts state-mekanisme.
  2. Direkte mutasjonEndrer for eksempel en state-array med items.push(newItem).
  3. Flere kopier av samme stateData kan komme ut av sync.
  4. All state i AppFlytter state høyere enn de som faktisk trenger den.
  5. Context på altGjør enkel dataflyt mer komplisert.
  6. Unødvendig prop drillingSender samme data gjennom mange nivåer når Context er passende.
  7. useEffect for beregningerBruker effect på noe som kan beregnes direkte under rendering.
  8. Uforklart KI-kodeKan ikke svare på hvem som eier state og hva som utløser rendering.

Rask repetisjon

Kortversjonen

  • React bygger UI av components.
  • JSX beskriver React-elementer med HTML-lignende syntaks.
  • Props flytter read-only data fra parent til child.
  • State er data som kan endres og påvirker UI.
  • useState brukes til lokal state.
  • Events utløser functions.
  • Callbacks lar child påvirke state hos parent.
  • State-eierskap bør ligge hos nærmeste felles eier som trenger dataene.
  • Rendering evaluerer UI-et på nytt når relevante data endres.
  • useEffect brukes til side effects og synkronisering utenfor ren rendering.
  • Context deler data i et subtree når prop drilling blir upraktisk.
  • Web Storage gir persistence; det er ikke React state management.

Data ned → handlinger opp → state endres → UI rendres.
